# MyCut — архитектура самостоятельных редакторов и графа связей

Версия: 0.1, редакция 4 — 13 октября 2026 года.
Статус: исходные требования и предложенная архитектура. Собственный MyCut Runtime и установщик ещё не созданы. Для обсуждения отсмотра подготовлен отдельный запускаемый прототип Windows на WPF/Windows PowerShell; он не является реализацией описанного ядра.

## 1. Зафиксированные требования пользователя

- Приложение для Windows; исходный код в GitHub; выпуск установщика.
- Один общий проект для монтажа, анимации и связанных материалов; отдельные фотодокументы могут существовать без видеопроекта и таймлайна.
- Фоторедактор — самостоятельное полноценное рабочее пространство, а не только инструмент обработки клипа.
- Аниматор — отдельная самостоятельная среда. Анимация свойств не переносится в фоторедактор; редакторы связываются опубликованными параметрами и направленными связями графа.
- Пример пользователя: интенсивность тени в фоторедакторе привязана к параметру X; аниматор изменяет X во времени. Референс взаимодействия — системы нод и шейдеров.
- Общее realtime-ядро обслуживает интерфейс и медиаредакторы. Интерфейс — интерактивная сцена, описанная нодами, связями, состояниями и событиями.
- Пользователь может открывать и изменять граф поведения/оформления интерфейса; панель параметров поддерживает структурирование и перетаскивание параметров по папкам.
- Интерфейс и названия нод сначала на английском; русская локализация планируется через отдельные языковые ресурсы.
- Новый приоритет: сначала прототип общего realtime-ядра и окна отсмотра; набор фоторедактора и остальные редакторы развиваются на этой основе.
- Рабочая папка пользователя на Windows: `D:\Приложение для пк\MyCut_v1`. Из текущей среды доступа к этому диску нет; файлы в этой папке не созданы и не проверены.
- Рабочие пространства: отсмотр, монтаж, анимация, Item Редактор с VFX, звук, цвет, экспорт.
- Item можно редактировать отдельно, использовать в видео и экспортировать как изображение.
- Изолированный просмотр Item, в том числе на чёрном фоне; таймлайн можно скрывать.
- Падение и скольжение с физикой, преимущественно в 2D, с возможностью 3D.
- Пространство сцены выходит за пределы кадра и не ограничивается разрешением видео.
- Система камер.
- Изучение удобных отдельных решений DaVinci Resolve, Blender, UE5 и FL Studio.

Далее описаны предлагаемые решения. Конкретные библиотеки, форматы файлов и значения по умолчанию ещё не утверждены.

## 2. Сцена, кадр и экран редактора

Сцена — пространство объектов. Кадр — результат наблюдения сцены камерой. Окно редактора — способ показать сцену или кадр пользователю. Эти три сущности разделены. Самостоятельный фотодокумент имеет собственный пиксельный холст и не требует пользовательской настройки камеры; связь с 3D-сценой описана в разделе 13.

Разрешение 1920×1080 определяет выходное изображение, а не размеры мира. Объект может находиться вне кадра, продолжать двигаться, сталкиваться с другими объектами и позже возвращаться в кадр.

Под «без границ» понимается отсутствие искусственной границы по краям кадра. Числовая точность компьютера конечна; бесконечная точность и неограниченные ресурсы не обещаются.

Предложение: мировые координаты хранить с двойной точностью; для GPU использовать координаты относительно камеры или локального начала. В первой версии достаточно работать в разумном диапазоне координат. Поддержку больших расстояний развивать отдельно.

## 3. Объекты и Item

| Сущность | Назначение |
| --- | --- |
| SourceAsset | Исходное фото, видео, звук, модель или другой ресурс |
| PhotoDocument | Самостоятельный документ: холст, слои, маски, содержимое и цветовые настройки |
| AnimationDocument | Самостоятельный документ: входные/выходные параметры, кривые, локальное время и связи |
| PublishedParameter | Типизированный интерфейс свойства для связи с другими документами |
| Binding | Направленная связь между выходом источника и входом получателя |
| ItemDefinition | Содержимое Item: ресурсы, слои, эффекты, вложенные сцены, анимация |
| ClipInstance | Размещение Item на таймлайне: начало, длительность, участок, преобразование времени |
| Scene | Объекты, камеры, свет и физические миры |
| SceneNode | Объект сцены с идентификатором, родителем и преобразованием |
| Camera | Проекция сцены и параметры кадра |
| PhysicsWorld | Настройки и состояние отдельной симуляции |
| ExportJob | Зафиксированное состояние проекта, диапазон времени, камера и настройки вывода |

Фото, видео, текст и векторные формы могут отображаться плоскими поверхностями в 3D-сцене. Эффекты, рассчитанные в пространстве Item, применяются до его размещения в сцене. Эффекты кадра применяются после камеры. Эти виды эффектов должны различаться.

Повторное размещение одного Item не должно неявно разделять изменяемое состояние физики. Общим может быть описание Item; экземпляры симуляции имеют отдельные идентификаторы. Совместное использование одной симуляции допускается только как явная связь.

Вложенная сцена имеет собственную область объектов, камер и времени. На родительском таймлайне её можно использовать как обычный Item.

## 4. Координаты и плоская работа

Предложенная система: X вправо, Y вверх, Z задаёт глубину; соглашение о направлении камеры фиксируется отдельно и проверяется при интеграции движка.

Размеры объектов задаются в единицах сцены. Для физики нужен явный коэффициент перевода в метры. Пиксели интерфейса, пиксели выходного изображения и физические единицы не смешиваются.

В плоском рабочем пространстве объекты по умолчанию редактируются на плоскости XY. Преобразование между координатами мира и экраном выполняет камера. Ввод размера в пикселях возможен как удобство интерфейса при известной камере, но не подменяет мировую систему координат.

Для простого монтажа должны существовать явный порядок слоёв и режим плоского отображения. Для 3D-композиции используется глубина сцены. Правила прозрачности, пересечения плоскостей и вложенных композиций потребуют отдельной спецификации.

## 5. Система камер

| Тип | Поведение | Основное применение |
| --- | --- | --- |
| Ортографическая | Размер объекта не меняется от расстояния до камеры | Фото, обычный монтаж, плоская анимация |
| Перспективная | Учитывает перспективу | 3D, пролёты, пространственный текст |

Предлагается создавать ортографическую камеру автоматически для новой композиции. Самостоятельный фоторедактор работает с холстом документа; камеры относятся к размещению материала в сцене и пространственной анимации.

Параметры камеры: положение, ориентация, размер ортографического обзора или угол обзора, диапазон глубины, соотношение сторон. Для анимации эти параметры публикуются и связываются с самостоятельным аниматором.

Нужны два независимых состояния:
- камера результата — определяет экспортируемый кадр;
- навигационный вид редактора — позволяет осматривать пространство вокруг кадра.

При просмотре «через камеру» рамка экспорта видна явно. Можно отдалить вид редактора и увидеть объекты за рамкой, не меняя результат экспорта.

Несколько камер могут существовать одновременно. На таймлайне композиции отдельная дорожка задаёт активную камеру и моменты переключения. В первой версии переключение мгновенное; смешивание между камерами — отдельная последующая функция.

Изоляция Item скрывает остальные объекты только для данного режима просмотра. Чёрный фон просмотра не добавляет чёрный слой и не уничтожает прозрачность. При отдельном экспорте Item пользователь выбирает его границы вывода или камеру; экспорт не должен случайно захватывать навигационный вид редактора.

## 6. Физика падения и скольжения

Первый набор параметров: тип тела (статическое, динамическое, управляемое анимацией), масса, гравитация, начальная скорость, форма столкновений, трение, упругость и затухание.

Визуальный объект и его форма столкновений — разные компоненты. Прозрачные пиксели фото не становятся автоматически сложным коллайдером. Первая версия предлагает прямоугольник, круг и простые выпуклые формы; автоматическое построение по контуру — отдельная функция.

2D-физика рассчитывает движение в плоскости выбранного физического мира. Результат переносится в координаты 3D-сцены. Плоскость 2D-мира в первой версии не меняется во время симуляции; движение камеры её не меняет.

3D-физика рассчитывает пространственное движение. 2D- и 3D-тела не сталкиваются друг с другом автоматически. Для контакта нужны общий физический мир или специально разработанный механизм связи.

Динамические тела рассчитываются в координатах физического мира. Взаимодействие с анимированными родителями и неравномерным масштабом требует явных ограничений. Предлагается в первой версии запрещать неподдерживаемые комбинации с понятным объяснением в интерфейсе.

Край кадра не является стеной. Если нужен бортик, пол или ограничивающая рамка, создаётся настоящий коллайдер. Он может быть невидимым в итоговом изображении.

## 7. Время, перемотка и повторяемость

Разделены:
- время композиции;
- локальное время Item;
- время симуляции;
- частота вывода кадров;
- время аудио в отсчётах.

Для таймлайна предлагается точное рациональное время. Физика работает с фиксированным шагом, независимо от скорости интерфейса. Конкретная частота шага выбирается после проверки выбранного решателя.

Чтобы перейти к произвольному моменту симуляции, движок восстанавливает подходящее контрольное состояние и рассчитывает последующие шаги либо читает заранее запечённые состояния. Пропуск отрисовки не означает пропуск физического расчёта.

Предлагаемое поведение изменения скорости: уже рассчитанное движение воспроизводится с новым преобразованием времени. Повторный расчёт с другой физической скоростью — отдельное явное действие. Обратное воспроизведение читается из сохранённых результатов; физический решатель не запускается «назад».

Повторяемость обеспечивается фиксированными настройками, шагом, начальным состоянием, случайным seed при необходимости и версией решателя. Побитовая идентичность разных платформ и GPU не обещается. Для точного воспроизведения между средами сохраняются необходимые результаты запекания.

## 8. Кэш и фоновые задачи

Кэши декодирования, прокси, композиции, физики и ресурсов GPU различаются. Ключ результата включает необходимые входы, их версии, настройки, время или диапазон времени и версию вычислительного модуля.

Примеры зависимостей:
- перемещение камеры пересчитывает отрисовку, но не физику;
- изменение трения пересчитывает зависимую симуляцию и её изображение;
- изменение цвета обычно пересчитывает изображение, но не движение;
- перемещение клипа меняет отображение локального времени; сохранённое локальное движение можно переиспользовать;
- изменение изображения влияет на физику только если форма столкновений зависит от него.

Объекты за пределами кадра могут не отрисовываться, но продолжают участвовать в нужной симуляции. Также учитываются их тени, отражения и другие влияния на видимые объекты. Простая проверка попадания в кадр не является достаточным условием для отключения вычислений.

Предпросмотр имеет приоритет над фоновыми задачами. Долгие задачи отменяются, а результаты устаревших задач не подменяют новую версию проекта.

Восстанавливаемый кэш можно удалить. Явно сохранённое запекание, необходимое для воспроизводимости и переноса проекта, хранится как отдельный ресурс проекта и не удаляется командой очистки временного кэша.

## 9. Сохранение и экспорт

Проект хранит версию схемы, идентификаторы ресурсов и объектов, сцены, камеры, связи, таймлайны, анимацию и параметры симуляций.

Автосохранение и атомарная запись предусматриваются до расширения набора функций. Состояние интерфейса, горячие клавиши и кэш не смешиваются с содержимым сцены.

Экспорт использует зафиксированное состояние проекта и выбранную камеру. Не использует навигационный вид редактора. Отрисовка и обработка эффектов должны использовать общую систему вычислений для предпросмотра и экспорта; уменьшенное качество предпросмотра обозначается явно.

Размеры вывода, цветовой профиль, прозрачность и диапазон времени задаются отдельно. Для прозрачного PNG фон просмотра не включается в результат.

## 10. Границы первой рабочей версии

План, а не уже выполненная реализация:
1. Фото и текст как плоские объекты в сцене.
   Перед размещением фото доступен самостоятельный PhotoDocument со слоями, базовыми масками, сохранением редактируемого документа и экспортом изображения. Это начальное подмножество будущего полного фоторедактора.
2. Ортографическая камера и навигация за пределами рамки кадра.
3. Анимация преобразований, общий и локальный таймлайны.
   Анимационные кривые создаются в самостоятельном аниматоре. Фоторедактор публикует параметры; связующий граф подключает к ним анимацию.
4. 2D-падение и скольжение по статической поверхности, сохранение состояний.
5. Изолированное редактирование Item, экспорт PNG и короткого видео.
6. Простая 3D-сцена, перспективная камера и минимальное столкновение в 3D для проверки расширяемости.
7. Сохранение/восстановление проекта и сборка Windows-установщика.

Интерфейсы 3D и физики предусматриваются с начала проекта. Реализация полноценного 3D-редактора, жидкостей, ткани, сложного моделирования и большого VFX-набора в этот этап не включена.

## 11. Проверяемые сценарии приёмки

- Объект расположен за краем кадра, входит в кадр и снова выходит; его координаты не обрезаются.
- Пользователь отдаляет навигационный вид; экспорт камеры не меняется.
- Камера движется, физическое падение объекта остаётся прежним.
- Объект скользит за кадром и сталкивается с расположенным там препятствием.
- Перемотка назад восстанавливает рассчитанное положение; повторный просмотр совпадает в пределах заданной точности.
- Экспорт кадра и качественный предпросмотр при одинаковых настройках дают согласованный результат.
- Изменение трения инвалидирует нужную симуляцию; изменение цвета не инвалидирует независимую физику.
- PNG из изолированного Item сохраняет прозрачность независимо от чёрного фона просмотра.
- Два независимых экземпляра Item не разделяют изменяемое физическое состояние.
- После сохранения и открытия проекта активная камера, связи объектов и движение восстанавливаются.

Это будущие проверки; они ещё не выполнены.

## 13. Самостоятельный фоторедактор

### 13.1. Поведение для пользователя

Действия «Открыть изображение» и «Создать изображение» открывают фотодокумент напрямую. Не требуют создания видеопроекта, FPS, длительности, дорожек или камеры.

PhotoDocument можно сохранить с редактируемыми слоями, закрыть и открыть снова. Экспорт в PNG/JPEG и другие выбранные форматы — отдельное действие и не заменяет сохранение редактируемого документа. Поддерживаемые форматы уточняются при реализации.

В приложении могут быть открыты несколько фотодокументов и видеопроект. Пользователь переключается между ними. Состояние сохранения и история отмены относятся к конкретному документу; независимые фото не получают общую случайную историю отмены. Внутри видеопроекта сохраняется согласованная история действий над его встроенными документами.

### 13.2. Модель документа

PhotoDocument включает:
- стабильный идентификатор и версию содержимого;
- размеры холста в пикселях, цветовой профиль и глубину цвета;
- растровые слои, группы, текст и формы;
- порядок слоёв, прозрачность, режимы смешивания и преобразования;
- маски и редактируемые корректировки;
- растровое содержимое, включая изменения от рисования и ретуши;
- связи с исходниками и встроенные ресурсы;
- метаданные документа.

Выделение, активный инструмент и масштаб просмотра — состояние редактирования. Перемещение и масштаб рабочего вида не меняют размеры или содержимое экспортируемого изображения.

Полный набор режимов смешивания, профилей, глубин цвета и видов корректировок вводится поэтапно. Самостоятельная модель документа предусматривается до реализации большого набора инструментов.

### 13.3. Планируемые инструменты

Целевой набор полноценного фоторедактора: выделения, перемещение и трансформация, обрезка и изменение размера, кисть и ластик, маски, текст и формы, корректировки цвета, ретушь и штамп. Перечень является планом возможностей, а не заявлением об уже готовой поддержке.

Первый вертикальный сценарий: создать/открыть фото → добавить слой → изменить изображение или маску → отменить/повторить действие → сохранить редактируемый документ → экспортировать PNG → открыть сохранённый документ снова.

### 13.4. Изображение и 3D-сцена

PhotoDocument хранит авторское содержимое в пространстве пиксельного холста. При размещении в видео Item ссылается на этот документ; результат документа отображается как плоский объект сцены. Мировой размер, положение, перспектива, движение и физика задаются на уровне размещения и сцены.

В цепочке сохраняются исходники → фотодокумент со слоями и корректировками → представление в Item → размещение на таймлайне. Переход в видео не требует ручного экспорта PNG и не уничтожает редактируемые слои. Подготовленное изображение или текстура является производным результатом, а не заменой документа.

Пример: исправить лицо и фон в фотодокументе; в аниматоре создать кривую приближения и связать её с преобразованием размещения фотографии. Исправление фотографии не удаляет ключевые кадры приближения. Изменение приближения не перезаписывает фотографию.

Предлагаются два явных варианта размещения: встроить документ в видеопроект либо связать внешний документ. Встроенные изменения отображаются сразу. Для внешних файлов нужна политика обновления и видимая версия; файл не должен молча изменять проект во время экспорта. Независимая копия документа создаётся отдельной командой.

### 13.5. Требования к движку изображений

Кисти, ретушь и маски требуют хранения изменяемого растрового содержимого. Они не сводятся к списку видеоэффектов. Предлагается плиточное хранение больших изображений и изменений, чтобы штрих кисти не копировал весь документ в истории отмены.

Размер холста и внутреннее качество изображения независимы от разрешения видеопроекта. Размещение большой фотографии в небольшом видео не уменьшает авторский фотодокумент.

Растровый движок, композитор слоёв и цветовая обработка используются и в самостоятельном фоторедакторе, и при вычислении соответствующего Item. Система документа доступна без запуска физики или 3D-сцены.

### 13.6. Дополнительные сценарии приёмки

- Фото открывается, редактируется и экспортируется без создания видеопроекта.
- Слои, маски и растровые изменения переживают сохранение и повторное открытие.
- PNG сохраняет прозрачность; JPEG использует явно заданную подложку.
- Изменение фотодокумента обновляет связанные Item и сохраняет их размещение и анимацию.
- Независимая копия фото редактируется без изменения оригинального документа.
- Экспорт видео не уменьшает разрешение исходного фотодокумента.
- Экспорт использует зафиксированную версию фотодокумента, даже если внешняя ссылка обновляется.

Эти сценарии также являются будущими проверками, а не результатами тестирования.

## 14. Самостоятельные среды и граф параметров

Этот раздел уточняет и имеет приоритет над прежними упрощёнными формулировками о создании анимации внутри фоторедактора.

### 14.1. Границы ответственности

Самостоятельность относится к рабочим средам и их документам: фоторедактор, аниматор, монтаж, звук, VFX и другие предметные редакторы. Это не требование создавать отдельный процесс Windows для каждой кнопки или дублировать движки. Каждый редактор имеет собственную задачу, инструменты и пригодный к самостоятельному использованию документ. Проект связывает эти документы.

| Среда | Создаёт и редактирует | Получает или передаёт другим средам |
| --- | --- | --- |
| Фоторедактор | Изображение, слои, маски, эффекты и статические настройки | Изображение и опубликованные свойства |
| Аниматор | Кривые, ключевые кадры, преобразования сигналов во времени | Значения параметров в момент времени |
| Монтаж | Размещения, длительности, переходы и композиционное время | Контекст времени, ссылки на документы и их экземпляры |
| Физическая среда | Тела, ограничения, начальные условия и симуляции | Рассчитанные положения и другие явно опубликованные результаты |
| VFX | Граф визуальной обработки | Изображения и типизированные параметры |
| Звук | Звуковые документы, обработку и автоматизацию | Аудио и явно разрешённые управляющие сигналы |

Название и выделение физической среды в отдельное окно ещё не определены. Таблица описывает ответственность, а не утверждённый набор кнопок интерфейса.

### 14.2. Пример с интенсивностью тени

1. В PhotoDocument пользователь добавляет эффект тени.
2. У свойства интенсивности выбирает «Опубликовать параметр».
3. Создаётся параметр с видимым именем X, типом Float, базовым значением и рекомендуемым диапазоном 0…1.
4. Свойство тени связывается с входным портом X фотодокумента.
5. В AnimationDocument пользователь создаёт кривую значения во времени.
6. Выход кривой связывается с входом X конкретного экземпляра фотодокумента.
7. При просмотре связанного проекта фоторедактор показывает результат с вычисленным значением X, оставаясь средой редактирования изображения.

Аниматор управляет значением X и не хранит реализацию тени. Фоторедактор хранит тень и её интерфейс и не требует собственной копии анимационного таймлайна.

X — пользовательское имя. Связь хранится через стабильный ParameterId, идентификатор документа и экземпляра. Переименование X не разрывает соединение и не путает его с координатой X объекта.

### 14.3. Контракт параметра

PublishedParameter включает идентификатор, отображаемое имя, владельца, направление порта, тип, единицы, базовое значение, рекомендуемый диапазон и политику выхода за диапазон. Типы расширяются поэтапно: Float, Integer, Boolean, Color, Vector2, Vector3, Transform, Image и Audio. Первый сценарий использует только Float.

Преобразование типов и диапазонов осуществляется явно: например, Remap связывает движение 0…100 с интенсивностью 0…1. Цветовой профиль, единицы и дискретность не теряются при неявном приведении. Неподдерживаемая связь отклоняется с понятным сообщением.

Свойства, несовместимые с непрерывным изменением или влияющие на структуру документа, не публикуются как произвольные покадровые сигналы. Доступные возможности указываются в описании параметра.

### 14.4. Базовое и вычисленное значения

Фоторедактор хранит базовое авторское значение. Связь даёт вычисленное значение в контексте времени. Просмотр кадра не перезаписывает базовое значение и не создаёт тысячу изменений в документе.

При подключённом драйвере панель свойства показывает вычисленное значение, источник и переход к нему. Редактирование базового значения и отключение драйвера — явные отдельные действия.

При самостоятельном открытии фотодокумента без проекта используется базовое значение, если пользователь явно не выбрал связанный контекст предпросмотра. При отключении связи возвращается базовое значение. Сохранение текущего вычисленного состояния как статического — отдельное действие.

### 14.5. Связи и переходы интерфейса

Вычислительная связь направлена: источник → получатель. Переход по ссылке в интерфейсе доступен в обе стороны: от свойства тени к кривой и от кривой к управляемому свойству.

Контекстное действие «Показать источник» открывает нужный редактор и выделяет кривую или узел. «Показать получателей» перечисляет зависящие свойства. Удаление свойства, документа или параметра сообщает о связанных получателях и не подставляет молча другой параметр по имени.

Для простого подключения достаточно действия в панели свойства. Общий визуальный граф позволяет видеть и редактировать несколько связей, преобразования и зависимости. Архитектура нод не обязывает пользователя собирать каждую простую операцию вручную.

### 14.6. Вычисление графа

Результат вычисляется из состояния документов, связей, времени, экземпляра и выбранного качества. Граф вычислительных зависимостей задаёт порядок обработки и область пересчёта. Он отделён от иерархии объектов сцены.

В первой версии у входа один источник. Несколько источников объединяются явным узлом Mix/Add/Multiply или другим подходящим оператором. Нельзя одновременно неявно управлять одним свойством из двух редакторов.

Обычные связи образуют ациклический граф. Циклы проверяются при соединении. Физика и другие состояния обрабатываются отдельными временными узлами с фиксированным шагом и сохранением состояния; произвольная обратная связь пока не поддерживается.

Вычислители эффектов и анимации доступны без открытого окна соответствующего редактора. Закрытие вкладки фоторедактора не выключает тень в видео. Экспорт выполняет тот же граф из зафиксированного состояния документов.

### 14.7. Время и экземпляры

AnimationDocument имеет собственное локальное время. Binding явно задаёт источник времени и преобразование: композиционное, время размещения или независимое время анимации. Запуск клипа не должен случайно запускать все копии анимации одновременно.

Параметр опубликованного документа описывает интерфейс; значение драйвера может относиться к конкретному экземпляру. Две копии одной фотографии могут использовать одинаковую тень, но получать разную интенсивность от двух анимаций. Изменение определения тени обновляет обе копии, а их управляющие значения остаются независимыми.

### 14.8. Проверяемый первый сценарий

Фоторедактор создаёт фото с тенью и публикует X. Самостоятельный аниматор создаёт кривую 0 → 1 → 0. Связующий граф подключает кривую к X. Проект воспроизводит изменение тени, поддерживает переход к обоим концам связи, сохранение и повторное открытие. Переименование X не ломает связь; отключение возвращает базовое значение; экспорт использует ту же кривую без открытых окон редакторов.

Это план реализации и приёмки. Код графа, отдельных редакторов и описанных функций ещё не создан.

## 15. MyCut Runtime: потоковый граф и интерфейс как сцена

Раздел фиксирует направление, согласованное после первого наброска окна отсмотра. Описанный движок ещё не реализован. Названия нод и элементов интерфейса далее приведены на английском.

### 15.1. Основной принцип

MyCut Runtime принимает события, изменения документов и потоки медиа; строит план нужных вычислений; переиспользует результаты; выдаёт состояние и изображения потребителям. Это потоковый вычислительный движок с графом зависимостей, планировщиком задач, кэшем и рендерером.

UI — интерактивная сцена с состоянием, компоновкой, графикой и обработкой ввода. В отличие от линейного видео, она реагирует на пользователя, размеры окна, фокус, доступность данных и другие события. Метафора «интерактивный видеоролик» описывает анимированное представление; семантика ввода и управление документами остаются обязательными частями.

Общими являются runtime, типизированные параметры, система анимации, управление ресурсами, GPU device и конечная композиция. Вычислительная нагрузка UI и медиа имеет отдельные очереди и бюджеты.

Экспорт получает ContentGraph и выбранную камеру. UIGraph и оформление приложения не попадают в экспорт. Общее ядро не смешивает рабочее пространство пользователя с авторским медиадокументом.

### 15.2. Четыре связанных представления

| Представление | Ответственность |
| --- | --- |
| EventGraph | PointerEnter, PointerLeave, PointerDown, PointerMove, Drop, FocusChanged и другие дискретные события |
| DataGraph | Типизированные параметры и потоки кадров, звука, текстур, геометрии |
| SceneGraph | Иерархия объектов, компоновка, преобразования, clipping и области hit testing |
| RenderGraph | Порядок GPU-проходов, ресурсные зависимости и конечная композиция |

Снаружи пользователь может видеть единый редактор нод с различимыми типами портов. Внутри это связанные представления с разными правилами исполнения. Их не нужно каждый кадр полностью обходить и перекомпилировать.

Сигнал состояния Hovered отличается от однократного события PointerEnter. Event-порт не подключается напрямую вместо числового значения, а Image/FrameStream не приводятся неявно к событию.

### 15.3. Очереди и время

- Platform/Input: события ОС, маршрутизация, фокус, захват указателя, ввод текста и IME.
- UI Runtime: события, состояние интерфейса, оценка активных анимаций, dirty layout и подготовка снимка сцены.
- Render: применение неизменяемого снимка сцены и композиция готовых GPU-ресурсов.
- Media Workers: чтение, декодирование, подготовка миниатюр/прокси и обработка медиа.
- Simulation Workers: последовательные физические шаги и сохранённые состояния.
- Background: предзагрузка, индексация, очистка кэша, экспорт с регулируемым бюджетом.

Это логические очереди, а не обещание фиксированного числа потоков ОС. Конкретное распределение устанавливается профилированием.

UIClock — монотонное время, связанное с обновлением экрана. MediaClock — timestamps исходника или время композиции. SimulationClock — фиксированный шаг физики. Скорость 0,5× видео не замедляет отклик кнопок и анимацию панели.

Интерфейс не ждёт декодер, диск или завершение тяжёлого GPU-эффекта. Когда новый кадр недоступен, отображается последний готовый или placeholder. Кадр применяется только если совпадают запрос, версия ресурса и текущий потребитель.

Наличие отдельных очередей не гарантирует отсутствие задержек на общем GPU. Потребуются ограничение длительности GPU-задач, небольшие пакеты, лимиты VRAM и отказ от синхронных ожиданий UI на незавершённых ресурсах.

### 15.4. Ноды интерфейса

Первый каталог: Window, Panel, Stack, Grid, ScrollView, VirtualList, Text, Image, VideoSurface, Button, Slider, FolderGroup.

Ноды поведения: PointerEnter, PointerLeave, PointerDown, PointerMove, DragStart, DragMove, Drop, HoverState, Delay, Condition, PreviewClip, CancelPreview, Tween, Spring, SetState и InvokeCommand.

Ноды связывают данные и семантические команды. Изменение документа выполняется командой с правилами undo и транзакций, а не прямой записью произвольной памяти из визуального узла. Переходы к редакторам используют стабильные идентификаторы документов и параметров.

Текст, ввод, выделение, буфер обмена, keyboard focus, DPI и доступность ОС должны учитываться в UI-элементах. Один только вывод текстуры панели не заменяет полноценный интерактивный интерфейс.

### 15.5. Пример Hover Preview

Предложенная связь:
- ClipCard.PointerEnter обновляет HoverState и запускает Tween для оформления.
- Через Delay 150 ms, если курсор ещё над той же карточкой и не идёт drag, запускается PreviewClip.
- PreviewClip получает SourceAsset, масштаб предпросмотра и токен актуального запроса.
- Поток готовых кадров передаёт текстуру в VideoSurface карточки.
- ClipCard.PointerLeave отменяет отложенный запуск/предпросмотр и возвращает оформление к обычному состоянию.
- Переход к следующей карточке отменяет устаревший запрос. Его поздний результат не появляется в новой карточке.

150 ms — исходное предложение для настройки, а не окончательная константа. По умолчанию hover preview без звука. Щелчок выбора и hover preview не меняют друг друга неявно: наведение не переключает выбранный исходник, его сведения или сохранённые границы.

Если нужных кадров пока нет, карточка немедленно реагирует визуально и показывает имеющуюся миниатюру. Кэш предпросмотра ограничен; сначала обрабатывается текущая карточка, затем небольшое ближайшее окружение.

### 15.6. Пример перетаскивания

PointerDown выполняет hit test. После порога движения начинается drag и захватывается указатель. DragMove обновляет временное положение объекта/drag ghost. Подсветка области Drop и движение окна связываются с состоянием drag через анимационные ноды.

Во время drag hover preview не запускается автоматически. Pointer capture сохраняет получение событий при выходе курсора за границы элемента. Escape отменяет действие; Drop создаёт одну команду документа. Временные координаты не порождают отдельную запись undo на каждое движение мыши.

Перемещение drag ghost следует текущему положению указателя без лишней задержки. Плавная анимация может применяться к подсветке и вспомогательным панелям, а не должна заставлять объект заметно отставать от мыши.

### 15.7. Анимация UI

Tween вычисляет значение из начального состояния, цели, easing и времени. Spring хранит необходимое состояние и выбирается там, где нужен характер движения. Новая цель берёт текущее видимое состояние: повторное наведение не сбрасывает элемент в начало анимации.

Преобразования, opacity и простые визуальные изменения по возможности обновляются без полного layout. Изменение ширины панели действительно может требовать пересчёта затронутой компоновки.

Нужны режим reduced motion, отключение необязательных эффектов, приостановка невидимых UI-анимаций и экономия работы при бездействии. Произвольная авторская анимация UI не обязана работать постоянно, если значение не меняется.

UI-анимации могут использовать тот же каталог кривых и параметров, что и самостоятельный аниматор. Для простого hover не требуется создание видеопроекта.

### 15.8. Как движок создаёт нужный кэш

NodeType описывает зависимости, входные форматы, допустимую точность, локальность операции, требования к CPU/GPU и возможность переиспользования результата. Runtime запрашивает данные от активных потребителей и выбирает поддерживаемое представление.

Примеры представлений: исходные пакеты видео, декодированный кадр CPU, GPU-текстура, уменьшенный кадр, миниатюра, плитки изображения, звуковые блоки и сводная звуковая волна. Создание прокси не всегда выгоднее прямого декодирования; оно выбирается политикой и измерениями.

Ключ результата включает NodeType/версию алгоритма, версии входов и параметров, временной диапазон, разрешение/качество, цветовой формат и необходимые особенности устройства. Большие исходники не хешируются заново каждый кадр: fingerprint и ревизии переиспользуются, а изменение файла проверяется отдельно.

Инвалидация учитывает вид изменения:
- Hover tint: paint/материал соответствующей карточки.
- Перемещение панели: transform или зависимый layout.
- Изменение текста: соответствующая компоновка и текстовые ресурсы.
- Новый кадр видео: новая текстура/проход, но не перестроение всей иерархии окна.
- Новая структура папок: затронутые строки и структура списка.

Часто изменяемый элемент не стоит каждый кадр целиком запекать в растровую картинку. Переиспользуются статическая геометрия, glyph atlas и неизменяемые ресурсы. VirtualList создаёт представления видимых строк и небольшого запаса, а не всех тысяч материалов одновременно.

Кэш имеет общие и категорийные лимиты RAM, VRAM и диска. Активные ресурсы защищены от преждевременного удаления до завершения использования GPU. Кэш не заменяет авторские документы и явные сохранённые запекания.

### 15.9. Визуальное перепрограммирование интерфейса

Команда Edit UI Graph открывает граф выбранной панели. Пользователь видит её входные данные, layout, состояния, анимации и события.

Для панели параметров предусмотрен режим Edit Layout: перемещение свойств по FolderGroup, переименование групп и изменение порядка. Это редактирует карту представления; идентификаторы свойств и их связи с аниматором остаются прежними.

Изменения имеют undo/redo и предпросмотр. Граф проверяется и компилируется вне активного кадра; новая версия заменяет старую целиком после успешной проверки. Некорректная версия не выключает текущий интерфейс.

UI-профили и графы оформления сохраняются отдельно от авторского медиадокумента. Reset Layout возвращает встроенный вариант. Для выбора документов и возврата рабочего интерфейса сохраняются необходимые системные команды.

В первой реализации редактируются разрешённые панели и готовые ноды. Расширение каталога нативными вычислителями и пользовательским кодом — отдельный последующий этап.

### 15.10. Графический backend и цвет

Общая система вывода получает сцены UI и контента и готовые ресурсы из RenderGraph. UI имеет собственную компоновку, clipping и экранные координаты; контент — камеры, пространство и управление цветом.

UI-цвета не подвергаются проектной цветокоррекции. Видеокадр приводится к цветовому пространству дисплея согласно настройкам просмотра, после чего компонуется с интерфейсом. Экспорт выполняется в выбранном выходном пространстве без UI.

Backend ещё не выбран. Возможны готовые GPU- и текстовые библиотеки с адаптером к MyCut Runtime. Ранее предложенный Qt/QML является кандидатом оболочки/отрисовки, но соответствие новому требованию общего движка должно быть проверено прототипом. Отдельный HTML-интерфейс не считается реализацией MyCut Runtime.

### 15.11. Язык интерфейса

Первый язык — English. Примеры разделов: Review, Edit, Animate, Item Editor, VFX, Audio, Color, Export. Примеры действий: Import, Mark In, Mark Out, Save Range, Edit UI Graph, Edit Layout, Reset Layout.

NodeTypeId, ParameterId и связи не зависят от отображаемой строки. Названия и описания хранятся через ключи локализации. Позже Language Pack добавляет русский без переименования типов нод и разрыва графов.

Ранее показанный русский набросок окна отсмотра фиксирует расположение и сценарии. При следующем обновлении интерфейса его надписи переводятся на English.

### 15.12. Первый прототип и критерии

Первый инженерный прототип должен проверить runtime на окне Review:
1. UIGraph создаёт панель, карточки и параметры.
2. PointerEnter/Leave запускают прерываемую Tween-анимацию.
3. PreviewClip асинхронно подаёт кадры и не блокирует ввод.
4. Кэш показывает попадания, пропуски, объём и причины пересчёта.
5. Edit UI Graph меняет одну связь; Edit Layout переставляет параметр без разрыва его связей.
6. Некорректный граф не заменяет рабочую версию; Reset Layout работает.

Цели плавности: поддержка 60 Hz и проверка 120 Hz на зафиксированной конфигурации. Полный интервал кадра составляет около 16,67 ms при 60 Hz и 8,33 ms при 120 Hz. Это цели и бюджеты, а не результаты измерений или гарантия для любого оборудования.

Измеряются p95/p99 времени кадра, пропуски обновлений, задержка от ввода до изображения, время декодирования, заполнение очередей и использование памяти. Сценарии нагрузки: тысяча материалов с виртуализацией, быстрое наведение между карточками, drag при холодном кэше, seek в тяжёлом видео, изменение графа во время просмотра.

Вычислительные циклы обычных связей отклоняются; stateful-анимация и физика имеют явные правила времени. Нельзя получить плавность только большим кэшем или единственной общей очередью.
